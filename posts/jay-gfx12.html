Why Jay is interesting

It caught my attention because Jay is developed as an SSA-based shader compiler with newer -imo better- heuristics so I tried to understand it a bit more. I read the papers mentioned, understood the algorithms and jay's IR model and the compiler's in-memory representation of programs

It first uses a spiller based on Braun & Hack's work on spilling and live-range splitting to decide which values will be spilled to memory and then uses a tree-scan register allocation algorithm based on Colombet et al. to.. allocate the registers ofc. The spiller also draws on Braun et al.'s "Simple and Efficient Construction of Static Single Assignment Form" to keep things in ssa form as spilling introduces new definitions. So even though NIR already comes in ssa, there's still work to do here :D

Jay uses a simpler per-lane SSA model and partitions the physical register file by stride before assigning values to it. So most of the compiler can work without dealing directly with all those Intel regioning rules.

BRW is not ssa-based and it supports lots of different architectures and over time it groweeeeed so MUCH. and for me its harder to follow, implement new features, find bugs etc. But NIR is ssa, so why leave that behind? Turns out the FS backend goes back to 2010 and NIR came in 2014. They have separate IRs, so NIR being ssa doesn't mean BRW has to be. But that still doesn't explain why BRW wasn't ssa-based in the first place. The papers already existed back then.. what were the tradeoffs? idk, I'd like to understand that part too.

On 28.09.2026 at XDC2026 (slides, video) Alyssa presented Jay, and a few days before that presentation jay became the default compiler for Xe2 and Xe3 hw in Intel. Huge success btw (MR), hoping to have the same success for gfx12.

Also, Alyssa's XDC results report 98% less spilling than BRW on a collection of game shaders. Pretty exciting :D (those are her results, I haven't benchmarked my gfx12 branch against BRW yet).

My working style

I firstly started with vkcube and then fixed accumulators. After that I had vkcube rendered in FS8 mode, then started going through CTS. An earlier run got stuck at test #6,418 (divbyzero_frag), and after some patches the latest FS8 run goes until 6,547 passed tests from a list of 28,399. Also 1,901 NotSupported, then test #8,449 crashed (helper_invocation.load_after_store). So 19,950 haven't run yet. Only FS is using jay here, other stages still use brw.

I hit a failed test on CTS then, if its a compiler assertion, run that test with GDB, run and bt then select the frame in jay, print the nir intrinsic name and figure out which part isn't handled yet, you know.. because it hit assertions... If its a misrender/miscompile instead, I compare the outputs and generated ISA. I mostly check what and how BRW handled that intrinsic and after I find the exact place that jay implements it (ofc the place around the assertion, but sometimes it may touch some other code too (see my partition patch)). Once I understand what BRW is preparing and what Jay already handles, sometimes the actual patch is almost trivial with jay abstractions :) then rerun the test to see if I actually fixed it, plus related tests and the relevant SIMD widths to check I didn't break something else.
